Using LazyAPI from AI agents ​

LazyAPI gives agents the same loop a developer uses in Postman: read the API, send requests, write tests, and run them. Results come back as structured data.

MCP server ​

bash
lazyapi mcp [--root dir]

This starts a Model Context Protocol server on stdio. Paths in tool arguments are relative to --root (default: the current directory). Paths that leave the root are rejected.

Register it with Claude Code:

bash
claude mcp add lazyapi -- lazyapi mcp --root /path/to/project

Or with any client that reads an mcpServers config:

json
{ "mcpServers": { "lazyapi": { "command": "lazyapi", "args": ["mcp", "--root", "/path/to/project"] } } }

Tools ​

ToolWhat it does
list_specsOpenAPI files under the root
list_operationsOperations of a spec (optionally by tag)
describe_operationParameters with examples, request/response schemas, referenced components, security, current test script
send_requestSend one operation (params, query, headers, body) and get request, response and every check
run_testsRun many operations. Only GET/HEAD/OPTIONS run unless methods is set (["all"] includes writes). Bodies are included only for operations that did not pass
run_flow / write_flowWrite and run .lazyapi/flows/<name>.js scenarios across operations; every step is checked against the spec
import_curl / export_curlAdd an operation from a curl command, or get the exact request as curl
read_test / write_testRead or write an operation's JavaScript test script; write_test links it via x-lazyapi-tests and reports compile errors
validate_specOpenAPI and LazyAPI checks (operationIds, responses, scripts compile)
script_apiThe TypeScript definitions of the script API

send_request accepts jq (e.g. ".items[0] | {id, status}") to return only part of a large body; checks still see the whole response.

send_request, run_tests and run_flow accept env_name to use a named environment from .lazyapi/config.yml (server, env file, variables and credentials).

Tool failures (network errors, unknown operations) come back as results with isError: true and a readable message, so the agent can fix the call and retry.

A server to test against ​

Data-driven checks: run --data rows.csv (MCP run_tests with data_file) runs the selection once per row with the row in the env; results carry iteration.

When a test creates data against a real API, export after(res) from its script to delete it: it runs even when the tests fail, so runs stay repeatable. See scripting.

lazyapi mock api.yml serves the spec's examples and validates incoming requests (422 with the reason). Agents can build and check tests before the real API exists, or reach error paths with Prefer: code=404. See mock.

CLI equivalents ​

Agents without MCP can use the CLI with JSON output:

bash
lazyapi list ops api.yml --json
lazyapi describe api.yml getUser --json
lazyapi send request api.yml --op getUser --param id=1 --output json
lazyapi types > .lazyapi/tests/lazyapi.d.ts
lazyapi run api.yml --output json            # exit 0 ok · 1 failed · 2 usage · 3 could not run

Validate an API in five steps ​

  1. list ops / list_operations: see what exists.
  2. describe / describe_operation: learn the parameters and the expected schemas.
  3. send / send_request: call it. The contract check already tells you whether the response matches the spec.
  4. write_test: encode the behavior you expect:
    js
    test("returns the user", () => {
  expect(response).toHaveStatus(200);
  expect(response.json()).toHaveProperty("email");
});
  5. run / run_tests: run everything. Commit the spec, tests/ and .lazyapi/lazyapi.lock so CI runs the same checks with --frozen-lockfile.
