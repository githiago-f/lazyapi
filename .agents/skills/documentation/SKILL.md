# LazyAPI Documentation Skill

This skill describes how to document the LazyAPI system: a Go + Bubbletea CLI/TUI for OpenAPI-driven API exploration.

## When This Skill MUST Be Used

- New exported Go symbol without a doc comment
- New CLI command or changed CLI args/flags
- New TUI page, tab, or field
- New auth scheme type
- New config/color/keybinding constant
- New env template prefix
- New example or use case
- Changes to architecture or data flow
- Any user-facing behavior change
- Adding or updating test plans in `.docs/plans/`
- Writing or updating the delivery harness in `.docs/`

## Per-Type Documentation Rules

### Go Doc Comments

- Every exported symbol must have a doc comment:
  ```go
  // FunctionName does X and returns Y.
  func FunctionName() Result { ... }
  ```
- Package doc comment in the first file of each package:
  ```go
  // Package store handles OpenAPI spec persistence.
  package store
  ```
- No comments on unexported symbols unless they are non-obvious.
- Use complete sentences ending with a period.
- For methods, describe what they do to/with the receiver:
  ```go
  // Send executes the HTTP request and returns the response.
  func (r *Request) Send() (*http.Response, string, error) { ... }
  ```

### Configuration

Update `docs/configuration.md` when:
- Adding new Catppuccin Mocha color constants to `config/config.go`
- Adding/removing keybindings in `config/keymap.go`
- Adding new page index constants in `config/pages.go`

### Authentication

Update `docs/authentication.md` when:
- Adding a new `AuthType` (e.g. `AuthDigest`)
- Adding new fields to `AuthScheme` struct
- Changing how auth is applied in the store layer

### Environment Variables

Update `docs/environment-variables.md` when:
- Adding a new template prefix (e.g. `{{secret.X}}`)
- Changing env loading/merging behavior
- Adding new fields to `env.Context`

### README.md

Update `README.md` when:
- Adding a new feature (add to feature list)
- Changing build/run instructions
- Adding new CLI commands
- Changing the project's purpose or scope

### AGENTS.md

Update `AGENTS.md` when:
- Adding new packages or restructuring directories
- Adding new key types or changing existing ones
- Changing architecture patterns
- Adding new known issues
- Changing build/test commands

## Doc Generation Pipeline

The vitepress documentation site is in `docs/`. To preview and build:

```bash
cd docs
npm install              # first time only
npm run extract          # extract Go doc comments to docs/data/extracted.json
npm run dev              # preview with HMR at localhost:5173
npm run build            # production build to docs/.vitepress/dist/
```

The `extract` script runs `bash scripts/extract-docs.sh` which uses `go doc` and `jq` to build a JSON metadata file. After adding new Go doc comments, run `npm run extract` to regenerate.

## Conventions

- Every vitepress page must have a title in its frontmatter (or inferred from the filename)
- Code blocks must have a language tag: `yaml`, `bash`, `go`, `json`
- CLI examples use `bash` with `$` prompt prefix
- Cross-reference with relative paths: `../cli/send.md`, `../tui/request-editor.md`
- Use `yaml` language tag for OpenAPI/YAML snippets
- Use `go` language tag for Go code snippets
- Every page should end with a "See also" section listing related pages
- Use [title case](https://apastyle.apa.org/style-grammar-guidelines/capitalization/title-case) for page titles and section headings
- Keep line widths to ~100 characters in markdown files for readability

## Updating Test Plans

Test plans live in `.docs/plans/` and follow a consistent format:

```markdown
# Plan: `<package>/<test_file>`

## Goal
<what the tests should verify>

## Test Cases

### `TestFunctionName_Scenario`
- <step-by-step test logic>
- <expected assertions>

### `TestFunctionName_EdgeCase`
- <edge case description>
- <expected behavior>

## Dependencies
- <packages, fixtures, or tools needed>

## Fixtures Needed
- <none or list of fixture files>

## Expected Coverage
- <percentage estimate or specific lines>
```

When adding a new test plan:
1. Create the plan in `.docs/plans/<NNN>-<short-name>.md`
2. Number sequentially (001, 002, etc.)
3. Update the README or AGENTS.md if a major testing milestone

## Updating the Delivery Harness

The delivery harness at `.docs/harness.md` is a mandatory pre-delivery checklist. When adding new documentation requirements, add corresponding checklist items.

## Updating Code Quality Docs

The code quality document at `.docs/feature/FIX.md` tracks known issues. When fixing a documented issue:
1. Mark it as resolved in FIX.md
2. Add a cross-reference to the PR or commit
3. Update the priority matrix if applicable

## Working with Lua Patterns

When searching for documentation targets, use these patterns:

- Find exported symbols without doc comments: `grep -r '^func [A-Z]' internal/ | grep -v '//\|^$'` (requires manual check)
- Find existing vitepress pages: `ls docs/**/*.md`
- Find Go doc extract issues: check `docs/data/extracted.json` for missing entries
