Environments & Auth ​

Everything LazyAPI keeps for a spec lives in a .lazyapi/ directory next to it, so it is versioned with the API (git-native). Only credentials and machine-local state stay out of git:

api/
  openapi.yml
  .lazyapi/
    config.yml           # environments: server, vars, http, auth   (committed)
    envs/<name>.env      # variables of an environment               (committed)
    secrets/<name>.env   # credentials of an environment             (git-ignored)
    tests/<op>.js        # test scripts (x-lazyapi-tests)            (committed)
    flows/*.js           # flows                                     (committed)
    data/*.csv|json      # data files for data-driven runs           (committed)
    lazyapi.lock         # pinned URL imports                        (committed)
    .local/              # drafts, history, caches                   (git-ignored)
    .gitignore           # secrets/ and .local/ (written by lazyapi)

LazyAPI writes .lazyapi/.gitignore when it creates the directory (for example on lazyapi import), and never overwrites it. LazyAPI looks for .lazyapi/config.yml next to the spec, then in the working directory.

.lazyapi/config.yml defines named environments. Each one sets a server, initial variables, HTTP options and credentials per security scheme:

yaml
default: local                 # used when no --env-name is given ($LAZYAPI_ENV also works)
environments:
  local:
    server: http://127.0.0.1:4010
    vars:                      # initial {{var.X}} values
      tenant: demo
  staging:
    server: https://staging.example.com
    auth:                      # keys are security scheme names from the spec
      bearerAuth:
        token: "{{env.API_TOKEN}}"      # API_TOKEN in secrets/staging.env
      apiKeyAuth:
        value: "{{env.API_KEY}}"
      basicAuth:
        username: "{{env.USER}}"
        password: "{{env.PASSWORD}}"
      oauth:
        clientId: "{{env.CLIENT_ID}}"
        clientSecret: "{{env.CLIENT_SECRET}}"
        scopes: "read write"   # optional: overrides the spec's scopes
      keycloak:                # OpenID Connect: endpoints discovered from the issuer
        issuer: https://sso.example.com/realms/acme
        clientId: lazyapi-cli
        grantType: authorizationCode   # or deviceCode, clientCredentials, password
  production:
    server: "1"                # an index into the spec's servers also works
    env: ../shared/prod.env    # optional extra env file, relative to this file
    http:                      # TLS, proxy and redirects for this environment
      caCert: certs/internal-ca.pem     # paths are relative to this file
      clientCert: certs/client.pem
      clientKey: certs/client-key.pem
      proxy: http://proxy.internal:3128
      noRedirects: false
      maxRedirects: 5
      insecure: false

Variables and secrets ​

The values of {{env.NAME}} for an environment come, in this order (later files win), from:

  1. the process environment;
  2. .lazyapi/envs/<name>.env: plain variables (base URLs, tenant ids, feature flags). Commit it;
  3. .lazyapi/secrets/<name>.env: tokens, passwords, client secrets. Git-ignored; written with mode 600 by LazyAPI;
  4. the environment's env: file, if any;
  5. --env <file> on the command line.

So the config and the variables are code that reviews and CI see, and each developer (or the CI secret store) provides secrets/<name>.env. In CI, write the file from the secret store before running, or export the variables in the process environment.

CLI flags such as --insecure or --proxy are combined with the environment's http settings.

Credentials ​

Credentials are applied to every request whose operation (or the spec, globally) requires that security scheme, including lazyapi.send() calls from scripts and flows. Empty values are never sent, so an Authorization header set explicitly or by before(req) is not overwritten by an empty scheme.

Scheme typeFields
http bearertoken
http basicusername, password
apiKey (header, query or cookie)value
oauth2, openIdConnectclientId, clientSecret; username + password (password grant); optional issuer (discovery), grantType, scopes, tokenUrl, authUrl, redirectUri, params; or a fixed accessToken

For the client-credentials and password grants, LazyAPI requests a token (client authenticated with HTTP Basic when it has a secret) and keeps it until shortly before expires_in. The authorization-code and device-code grants need you to log in once: the TUI does it when you send, the CLI with lazyapi login. Sessions are stored in .lazyapi/.local/tokens.json (git-ignored) and refreshed automatically. A failed token request fails the operation with the token server's answer. See Authentication.

Upgrading from 1.3 ​

1.4 reads only the .lazyapi/ layout. To move a project:

bash
mkdir -p api/.lazyapi/envs api/.lazyapi/secrets
git mv api/lazyapi.config.yml api/.lazyapi/config.yml
git mv api/tests api/.lazyapi/tests
git mv api/flows api/.lazyapi/flows
sed -i 's#x-lazyapi-tests: tests/#x-lazyapi-tests: .lazyapi/tests/#' api/openapi.yml
printf 'secrets/\n.local/\n' > api/.lazyapi/.gitignore

Then split each environment's old .env.<name>: plain values into .lazyapi/envs/<name>.env (commit it), credentials into .lazyapi/secrets/<name>.env, and drop the env: keys from config.yml. Scripts that used pm.* must use the native API (re-importing the collection translates them).
